### 2.2 踏んだ罠

**文字化け（aisin.com）** — `requests` が HTTP ヘッダーの `Content-Type: text/html` に charset 指定がないため ISO-8859-1 と誤判定し、日本語が壊れた。HTML 側の `<meta charset>` は utf-8 なので気付きにくい。`resp.encoding = 'utf-8'` を明示して解決した。**charset 指定のないサイトでは常に起こりうる**ので、他サイトを追加する際は必ず確認すること。

**406 Not Acceptable（imra.com）** — WordPress がユーザーエージェント等でボットを弾いている。ブラウザ相当のヘッダー3種で通る。

**SSL 証明書エラー（imra.eu）** — `unable to get local issuer certificate`。`curl -k` で回避できることのみ確認したが、原因は未調査。加えて imra.eu は論文一覧ページを持たず、個別ニュース記事として散在しているため構造化のコストが高い。**このサイトのスクレイピングは断念し、Web of Science の `OG="IMRA Europe"` 検索に置き換えた**（25件回収）。

## 3. 段階[2] OpenAlex への対応づけ

スクリプト: `src/openalex_link_toyota_papers.py`（357行）

### 3.1 正規化関数は3種類あり、用途が違う

混同しやすいので明記する。

| 関数 | 場所 | 用途 | 挙動 |
|---|---|---|---|
| `normalize_doi` | `openalex_link_toyota_papers.py:61` | DOI の照合キー | `https://doi.org/` プレフィクスを剥がし、末尾のピリオドを落とし、小文字化。`10.` で始まらなければ `None` |
| `normalize_title` | `:72` | 類似度計算の入力 | NFKC 正規化 → 小文字化 → 英数字・かな・漢字**以外**をすべて空白に → 空白圧縮 |
| `clean_for_search` | `:80` | OpenAlex への検索クエリ | 英数字・空白・CJK 以外を空白に落とし、300文字で切る |

`clean_for_search` を別に用意しているのは API 側の制約による。**カンマはフィルタの区切りとして解釈され、`*` `?` はワイルドカード扱いになって stemmed フィールドでは HTTP 400 を返す。**コロンやパイプもフィールド指定と誤解釈される。タイトルにこれらが含まれるのは普通なので、専用のサニタイズが要る。

### 3.2 DOI 完全一致（637件）

OpenAlex の OR フィルタ上限に合わせて **50件ずつバッチ**で問い合わせる（`DOI_CHUNK = 50`, `:58`）。

```
filter=doi:{doi1}|{doi2}|...|{doi50}&per-page=50&select=...
```

これが無料枠の節約に効いている。641件のユニークDOIが13リクエストで済む。**1日1,000リクエストという制限は、1リクエストあたり50件取れるので実質1日5万件**になる。この設計がなければ今回の規模でも数日かかっていた。

ただしバッチは丸ごと失敗することがある（レート制限等）。そこで **バッチ後に取りこぼしを個別に再取得するフォールバック**を入れてある（`:222-234`）。1件も取れなかったバッチには `← 要再取得` を出力する。

`select` で取るフィールドは `:48-52` に定義。`id, doi, title, publication_year, type, cited_by_count, referenced_works_count, authorships, primary_topic, topics, primary_location, institutions_distinct_count`。後段の指標計算に必要なものだけを指定して応答サイズを絞っている。

### 3.3 タイトルのファジーマッチ（216件）

DOI がない論文について、次の手順を踏む。

1. `filter=title.search:{cleaned}` で最大10件の候補を取る
2. 0件なら `search={cleaned}`（全文検索）にフォールバックする
3. 各候補について `SequenceMatcher(None, 正規化した元タイトル, 正規化した候補タイトル).ratio()` を計算
4. 最良スコアでしきい値判定

```python
AUTO_THRESHOLD   = 0.95   # これ以上は自動採用
REVIEW_THRESHOLD = 0.80   # これ以上0.95未満は目視に回す
                          # 0.80未満は no_match（記録せず捨てる）
```

`SequenceMatcher` は Python 標準の `difflib` にある編集距離ベースの類似度で、外部依存を増やさずに済む。文字レベルの比較なので、副題の有無や記法の差（`--` と `–`、ギリシャ文字の綴り）で 0.85〜0.95 に落ちる。この帯域がまさに「機械では判断できないが人なら分かる」領域であり、そこを目視に回す設計になっている。

**実際に目視に回ったのは10件のみ**だった。919件のうち0.9%以下である。しきい値の置き方としては妥当だったと考えている。

### 3.4 キャッシュとクォータ枯渇の扱い

`get()`（`:116`）が全リクエストを通る唯一の入口になっており、ここでキャッシュ・リトライ・予算管理をすべて行っている。

- キャッシュキーは `json.dumps(params, sort_keys=True)`。パラメータが同一なら再送しない
- 25件ごとにディスクへ書き出す（`:140`）。途中で落ちても失わない
- HTTP 429 を受けたとき、`X-RateLimit-Remaining` ヘッダーが `0` なら **1日の予算切れ**と判断して `BudgetExhausted` を投げ、それ以外は一時的スロットリングとみなしてバックオフする（`:143-151`）。この区別が重要で、区別しないと予算切れの日に無駄なリトライを繰り返す
- `BudgetExhausted` は `main()` で捕まえ、**それまでの結果を保存してから正常終了する**（`:301-312`）。翌日リセット後に再実行すればキャッシュ済み分はクォータを消費せず、続きから進む
- `polite pool` を使うため `mailto` を全リクエストに付けている（`:44`）。10 req/秒・100k/日の枠に入る
- 各リクエスト前に `time.sleep(0.15)` を入れている

入出力パスは環境変数（`SCISCI_INPUT_CSV` / `SCISCI_OUT_DIR` / `SCISCI_CACHE_PATH`）で差し替えられる（`:37-41`, `:96`）。launchd による自動実行が Drive 外の `~/scisci-auto/` で動くための仕組みである。

### 3.5 目視確認を別スクリプトに分離した理由

`src/apply_review_decisions.py`（81行）が担当する。

対応づけ本体は毎日自動実行され、`openalex_links.csv` を**作り直す**。目視の判断を直接そこへ書き込むと翌朝には消える。そのため、

- 判断は `data/review/openalex_review_decisions.csv` に人手で残す（列: `row_id, source_org, title, openalex_id, match_score, matched_title, decision, reason, reviewed_by, reviewed_on`）
- `apply_review_decisions.py` が毎回それを上から適用し、`openalex_links_reviewed.csv` を出す
- `decision == "reject"` なら `openalex_id` を `None` に戻し、`review_status` を `rejected_by_review` にする（`:49-53`）
- `row_id` は入力CSVの行番号であり、自動生成側と判断表で同じ行を指す

**判断の履歴が残ることに意味がある。** 今井先生の「目視確認が必要」という指示への対応が、後から検証可能な形で残る。

判断内容（全10件）:

| row_id | 収集元 | スコア | 判断 | 理由 |
|---:|---|---:|---|---|
| 1, 96, 100, 105, 118 | 未来創成センター | 0.87〜0.94 | accept | 副題・記法の差のみで同一論文と確認 |
| 704, 706, 727, 841 | AISIN IMRA 米国 | 0.83〜0.95 | accept | 同上 |
| 745 | AISIN IMRA 米国 | 0.83 | **reject** | 掲載誌（Adv. Solid State Phys. vs Semicond. Sci. Technol.）・年・種別が異なる別論文。正しい対応先は OpenAlex 未収録（Springer 書籍シリーズの章） |

### 3.6 検出できない誤り — OpenAlex 側のメタデータ破損

**このスクリプトの設計上の前提が一つ崩れている。**

コード冒頭のコメントには「DOI があれば誤同定の余地がないので自動採用」と書いてあるが、これは成り立たない。実例:

| DOI | 実際の論文 | OpenAlex が返す書誌 |
|---|---|---|
| `10.1364/ol.37.003084` | Optics Letters 2012年、周波数コム | **1946年のスペイン語眼科論文**「Problemas que plantea la queratoplastia」 |
| `10.1364/ol.20.000195` | Optics Letters 1995年 | **1968年の天文学論文**「INFLUENCE OF A STELLAR DENSITY GRADIENT...」 |

DOI は両側とも一致しているのに、OpenAlex が別論文の書誌を紐づけている。**こちらの照合ロジックでは原理的に検出できない。**

初期のレポートに「AISIN IMRA 米国法人は最古が1946年」と書いてしまったのはこの破損レコードを拾ったものである。現在の対応づけデータにも2件ともそのまま残っている（`publication_year` が1980年未満の論文はこの2件のみ）。

**対処案: 出版年の外れ値を検算に使う。** 組織の設立年より前の論文、あるいは収集元サイトの掲載範囲から極端に外れた年の論文をフラグ立てして目視に回す。今回のケースでは、この規則で2件とも捕まる。未実装。

## 4. 段階[3][4] 欠損値補完

### 4.1 Crossref（`src/enrich_papers_crossref.py`、212行）

**なぜ OpenAlex ではなく Crossref を使うのか。** OpenAlex は無料枠が1日1,000リクエストなのに対し、Crossref は 10 req/秒・日次上限なしで使える。**OpenAlex のクォータが尽きた日でもこの処理は進められる**。役割を分けておくことで、1日の作業がクォータに縛られない。

- エンドポイント: `https://api.crossref.org/works/{doi}`（1件ずつ）
- `time.sleep(0.15)` で 10 req/秒 に余裕を持たせる
- 404（Crossref 未登録）は `None` をキャッシュに入れて再照会しない（`:94-96`）
- キャッシュは50件ごとに書き出し
- 出力は論文単位（`crossref_papers.csv`）と論文×著者単位（`crossref_authors.csv`）の2つ

著者レコードの列: `doi, author_position, given, family, full_name, orcid, affiliation, is_toyota_affiliated, is_corresponding`。

トヨタ系判定は所属文字列に対する単純な部分文字列一致（`:41-44`, `:105-109`）:

```python
TOYOTA_PATTERNS = ["toyota", "imra", "aisin", "tytlabs", "豊田", "トヨタ", "アイシン"]
```

NFKC 正規化して小文字化したうえで、いずれかを含むかを見る。**この単純さが §6.2 の誤判定を生んでいる。**

### 4.2 Scopus（`src/enrich_papers_scopus.py`、254行）

#### 4.2.1 著者検索を捨てた理由（実測値つき）

当初の設計は「Scopus で著者を検索し、その著者の現所属を得る」だった。二つの理由で破棄した。

1. **`ORCID()` 検索が機能しない。** 論文数上位6名すべてで0件だった。HTTP 200 で空結果が返るので構文は正しく、Scopus 側に ORCID がほとんど登録されていないということである。
2. **著者名検索は同姓同名を絞り込めない。** `AUTHLASTNAME(Suzuki)` は45,844件、`AUTHLASTNAME(Kan)` は5,235件が該当する。パイロット検証で定量化した問題と同一である。

補足として、Author Search の構文には注意点がある。`AUTHOR-NAME()` という複合フィールドは Author Search（`content/search/author`）では `INVALID_INPUT` になり、`AUTHLASTNAME()` と `AUTHFIRST()` を `AND` で分ける必要がある。一方 Scopus Search（`content/search/scopus`）は `AUTHOR-NAME()` を受け付ける。**別物なので混同しないこと。**

また `AF-ID()` による厳密な機関絞り込みは `AFFIL()` の自由文字列一致よりはるかに取りこぼしが多い（試行した8名すべてで `AF-ID()` は0件、`AFFIL(Toyota)` は複数名で数件〜10件ヒット）。Toyota 関連の af-id は地域・部門ごとに25件以上に細分化されているためである。

#### 4.2.2 採用した方式

**Abstract Retrieval で論文（DOI）から所属を引く。**

```
GET https://api.elsevier.com/content/abstract/doi/{doi}?view=FULL
Header: X-ELS-APIKey
```

どの論文かは既に確定しているので、**人物同定の曖昧さが原理的に発生しない**。これが今回の設計上の要点である。

応答の構造に一つ癖がある。**著者オブジェクトは所属の名前を持たず、所属IDしか持たない。** そこで論文全体の `affiliation` 配列から `@id → affilname` の対応表を作り、著者側の `@id` を引き直している（`:152-165`）。

```python
afid_to_name = {af["@id"]: af.get("affilname") for af in as_list(d.get("affiliation"))}
...
afids = [x.get("@id") for x in as_list(a.get("affiliation"))]
names = [afid_to_name.get(i) for i in afids if afid_to_name.get(i)]
```

もう一つの癖として、**Scopus は要素が1つのとき配列ではなく辞書を返す**。`as_list()`（`:83-87`）で吸収している。これを忘れると単著論文や単一所属の論文でクラッシュする。

クォータ管理: Abstract Retrieval は 10,000/週。641件なので余裕がある。HTTP 429、または 403 かつ本文に `QUOTA` を含む場合を `QuotaExhausted` として扱い、途中結果を保存して終了する（`:113-116`）。400/404 は Scopus 未収録として `None` をキャッシュする。

#### 4.2.4 Crossref 著者レコードとの突き合わせ

`aggregate_researchers.py:113-145` の `merge_scopus_affiliations()` が担当する。

突き合わせキーは **`{DOI}|{姓}|{名の先頭イニシャル}`**。

```python
s["match_key"] = [f"{doi}|{name_key(given, surname)}" for ...]
```

**DOI で論文を固定したうえで著者を照合している点が肝である。** 1論文の著者は数名〜数十名しかいないので、この粗い粒度でも取り違えはほぼ起きない。逆に著者名の全体一致を要求すると、Crossref と Scopus で表記が違う（`Martin E.` vs `M.E.`）ために大量に落ちる。**粒度を粗くすることで表記ゆれに強くしている。**

同一論文内に同じキーが複数ある場合（同姓同名の共著者）は先頭を採る（`:134`）。

結果、Crossref 著者レコード3,206件のうち **2,476件（77.2%）** に Scopus の所属を付与できた。

著者レコード単位の所属網羅率:

```

Scopus 統合後    81.1%
トヨタ系判定      680件 → 1,627件
```

統合列は2つ:

```python
a["affiliation_any"] = a["affiliation"].fillna(a["scopus_affiliation"])   # どちらかにあれば
a["is_toyota_any"]   = a["is_toyota_affiliated"] | a["scopus_is_toyota"]  # どちらかがトヨタ系なら
```

Crossref を優先しているのは、Crossref の所属が「出版社が登録した、その論文執筆時点の所属」であり、Scopus の `affilname` より粒度が細かい（部署名を含むことがある）ためである。

## 5. 段階[5] 名寄せと集約

スクリプト: `src/aggregate_researchers.py`（271行）

### 5.1 なぜ既存の著者識別子を使わないのか

**OpenAlex Author ID も WoS ResearcherID も、過剰併合していることを実測で確認している。**

| 識別子 | 確認した問題 |
|---|---|
| OpenAlex Author ID | 同姓同名の別人が1つの ID に併合されている。「S. Nakamura」の研究歴は74年 |
| WoS ResearcherID | 2022年に発行された ID に1970年代の論文が紐づいている |
| **ORCID** | **クリーン。** 383件中368件が単一の氏名表記だけに対応し、同じ氏名が複数 ORCID に分かれているのは4件のみ |

ORCID がきれいなのは、研究者自身が登録する identifier だからである。機械的に推定された識別子とは性質が違う。

**したがって ORCID を最上位の権威とする。** ただし ORCID が付いているのは全レコードの約24%（779/3,206）にすぎないので、残りは氏名から作ったキーで寄せる。

### 5.2 氏名キーの定義

```python
def name_key(given, family):     # aggregate_researchers.py:51
    return f"{norm(family)}|{norm(given)[0]}"     # 姓 + 名の先頭1文字

def full_key(given, family):     # :61
    return f"{norm(family)}|{norm(given)}"        # 姓 + 名の全体
```

`norm()`（`:42`）は NFKC 正規化 → 小文字化 → 英数字・かな・漢字・空白以外を空白に → 空白圧縮。全角半角・大文字小文字・ピリオドの有無を吸収する。

`name_key` を採るのは、**「Martin E. Fermann」「M. E. Fermann」「M.E. Fermann」を1人にまとめるには、名の先頭1文字までしか使えない**ためである。フルネームを要求すると、イニシャル表記のレコードがすべて別人になる。

`full_key` は比較対照として計算しているだけで、クラスタリングには使っていない。

### 5.3 誤り率を実測する設計（この処理の核心）

氏名キーは当然誤る。姓と名のイニシャルが同じ別人を併合する。**問題は「誤る」ことではなく「どれくらい誤るか分からない」ことなので、それを測る。**

`validate_namekey()`（`:77-110`）が行う。

> **ORCID が付いているレコードだけを取り出し、ORCID を正解ラベルとみなして氏名キーの誤りを数える。**

- **過剰併合**: 1つの氏名キーに複数の ORCID がぶら下がる ＝ 別人を1人にまとめている
- **過剰分割**: 1つの ORCID が複数の氏名キーに割れる ＝ 同一人物を別人にしている

実測結果（`data/derived/researchers/namekey_validation.json`）:

```
正解ラベルつきレコード   779件
ユニーク ORCID         383件

name_key（姓+イニシャル、採用したもの）
  ユニークキー          369
  過剰併合したキー       16 (4.3%)
  過剰分割した ORCID      4 (1.0%)
  例: hatanaka|t, inoue|d, ishigaki|m, mizuno|h, nagai|y   （いずれも2 ORCID）

full_key（姓+名フル、比較用）
  ユニークキー          393
  過剰併合したキー        4
  過剰分割した ORCID     14 (3.7%)
```

**トレードオフがはっきり見える。** キーを厳しくする（`full_key`）と過剰併合は 16→4 に減るが、過剰分割が 4→14 に増える。今回は「同一人物を取り逃がすより、別人が混ざるほうが後で検出しやすい」と判断して `name_key` を採った。混ざった別人は所属や出版年の不整合として現れるが、分割された同一人物は探しに行かないと見つからない。

**この実測値には既知のバイアスがある。** ORCID を持つ層はフルネームが記録されている層に偏っている。したがって「イニシャル表記しかない著者」の誤り率は、この4.3%より悪い可能性が高い。だから低確信度として隔離している（§5.5）。

### 5.4 クラスタリング

`:179-193`。ORCID を優先し、なければ氏名キーを使う。

```python
# 同じ ORCID を持つレコードが属する氏名キーは、すべて同一人物とみなして統合する
key_to_orcid = {}
for orcid, grp in a[a["orcid"].notna()].groupby("orcid"):
    for k in grp["name_key"].unique():
        key_to_orcid[k] = orcid if k not in key_to_orcid else "__CONFLICT__"

def cluster_id(row):
    if pd.notna(row["orcid"]):                     # 本人が ORCID を持つ
        return f"orcid:{row['orcid']}"
    mapped = key_to_orcid.get(row["name_key"])     # 同じ氏名キーの誰かが ORCID を持つ
    if mapped and mapped != "__CONFLICT__":
        return f"orcid:{mapped}"
    return f"name:{row['name_key']}"               # ORCID の手がかりなし
```

ポイントは2つ。

1. **ORCID を持つレコードから、持たないレコードへ ID を伝播させている。** 同じ人物が論文Aでは ORCID つき、論文Bでは ORCID なしで登録されている場合を拾う。
2. **`__CONFLICT__` の扱い。** 1つの氏名キーに複数の ORCID が対応する場合（＝過剰併合が起きているキー、実測16件）、伝播を止めて氏名キーのまま残す。曖昧なものを無理に統合しない。

| **low** | 氏名キーで寄せた。**かつイニシャル表記しかない** | 154 |

low を分けているのは §5.3 のバイアス（イニシャル層で誤り率が悪化する可能性）に対応するためである。この154名は目視確認に回す。

`is_initials()`（`:64-74`）に一つ罠がある。素朴に正規表現 `^([A-Za-z]\.?\s*)+$` で判定すると、`Donald` のような普通の名前にもマッチしてしまう（1文字ずつの繰り返しで全体を消費するため）。トークンごとに1文字かを見る実装に直してある。**この種のバグは静かに大量の研究者を low に落とすので気付きにくい。**

## 6. ノイズ除去の4層（詳細）

### 6.1 層① 対応づけの誤り

| 誤りの種類 | 検出できるか | 対処 | 実測 |
|---|---|---|---|
| タイトル類似だが別論文 | できる | しきい値0.80〜0.95を目視に回す | 10件中1件を取り消し |
| DOI 一致だが OpenAlex 側の書誌が別論文 | **できない** | 出版年の外れ値検算（未実装） | 2件残存 |
| 同一論文が複数行に対応（正常な重複） | できる | Work ID 単位で重複排除 | 7件 |

### 6.2 層② 所属判定の誤り（未対処の課題）

トヨタ系判定は `TOYOTA_PATTERNS` の単純な部分文字列一致である。この単純さが偽陽性を生む。

**確認済みの誤判定: `Toyota Technological Institute`（豊田工業大学）が2レコード、トヨタ系と判定されている。** 豊田工業大学は STATUS.md で「トヨタ自動車の出資で設立されたが企業の研究所ではなく教育研究機関であり、本研究の趣旨から外れるので除外を提案する」と書いた組織そのものである。判定ロジックと分析方針が食い違っている。

現在は2件と小さいが、**対象組織を広げる判断が下りた瞬間にこの問題は拡大する**（WoS では豊田工業大学が6,295件ヒットする）。所属正規化とあわせて対処すべきである。

同種の偽陽性候補: `Toyota Technological Institute at Chicago`、地名や人名としての "Toyota"、`Aisin` を含む無関係な組織。

### 6.3 層③ 名寄せの誤り

§5.3 の通り、ORCID を正解ラベルとして実測済み（過剰併合4.3%・過剰分割1.0%）。実測値を確信度に反映し、低確信度154名を隔離する形で扱っている。

**「捨てる」ではなく「隔離する」という扱い方が重要である。** 詳細は次項。

### 6.4 層④ 母集団そのものの誤り（受領した著者リストの検証）

`docs/reports/pilot_scopus_wos_verification.md` に全文がある。要点のみ。

Sota Hayashi さんから受領した `toyota_data/toyota_authors.csv`（9,429名、OpenAlex 由来）が分析の主データとして使えるかを確かめるため、層化サンプリングした100名を Scopus と WoS で一人ずつ照合した（乱数シード `20260803`、511 API 呼び出し、エラー0件）。

| 層 | 定義 | 母集団 | 抽出 | 裏付け率 | 同姓同名フラグ率 |
|---|---|---:|---:|---:|---:|
| `current_other` | 現所属・スイス法人経由でない（対照群） | 1,670 | 35 | **62.9%** | 14.3% |
| `current_swiss` | 現所属・スイス法人エンティティ経由 | 1,984 | 35 | **48.6%** | 17.1% |
| `known_noise` | `first_pub_year < 1960` またはキャリア長 > 60年 | 1,250 | 30 | **30.0%** | **76.7%** |

**判定設計で一度失敗している。** 初版は「`AU=X AND OG=Toyota` がヒットしたら所属の証拠」としていたが、これは誤りである。この複合クエリは「X と同姓同名の**別人**がトヨタと共著していた」場合にもヒットする。証拠として、WoS のみを根拠に「確認済み」とした12名は名前のみヒット数の中央値が **862件**、Scopus とも一致した20名は中央値 **9.5件** だった。桁が2つ違う。

そこで「名前のみヒット数 > 50」を**ありふれた名前の代理指標**とし、この場合は WoS 単独の証拠を採用しないよう判定を作り直した（`src/pilot_revise_verdicts.py`）。**この代理指標は1著者1クエリで取れるので安価であり、今後も併記すべきである。**

**最も重要な発見: `known_noise` 層の本質は「トヨタと無関係」ではなく「ありふれた名前による識別子の併合」である。** 同姓同名フラグ率が76.7%（他層は14〜17%）という数字がそれを示している。

したがって **「ノイズだから捨てる」のではなく「ID 併合が起きているから分割が必要」と捉えるべきである。** 実例として `Shinji Inagaki`（キャリア61年、Scopus 現所属は産総研）は WoS でトヨタグループに133件ヒットしており、**豊田中央研究所の実在の研究者が ID 併合によって汚れている**と考えられる。捨てれば実在の研究者を失う。

スイス法人経由で矛盾した11名の所属は、東京大学・金沢大学・三菱総合研究所・慈恵医大・Karadeniz Technical University など、トヨタとまったく関係のない機関が並んだ。**既知バグ（スイス法人への誤帰属）は「豊田中研の混入」だけではなく、より広範な誤帰属を含む。**

`no_evidence`（両DBに候補なし）をノイズと断定してはいけない。現所属層でも各5名出ており、Scopus/WoS 未収録の可能性がある。

## 7. 補完に使わなかった経路と、その理由

記録として残す。試して外したものを再度試さないため。

| 試したこと | 結果 | 外した理由 |
|---|---|---|
| Scopus `ORCID()` 検索 | 上位6名すべて0件（HTTP 200・空結果） | Scopus 側に ORCID がほぼ未登録 |
| Scopus Author Search で所属取得 | `AUTHLASTNAME(Suzuki)` = 45,844件 | 同姓同名を絞り込めない |
| Scopus `AF-ID()` 厳密一致 | 試行8名すべて0件 | af-id が地域・部門ごとに25件以上に細分化されており取りこぼしが大きい。`AFFIL()` の自由文字列一致を使う |
| WoS を所属の間接証拠に使う | Scopus が見つけられなかった所属を**1件も新規発見しなかった**（`wos_support`・`group_support` とも全層0件） | 費用対効果が悪い。WoS の価値は「新規発見」ではなく「Scopus の判定の確信度を上げること」にある |
| OpenAlex Author ID を名寄せに使う | 「S. Nakamura」の研究歴74年 | 過剰併合 |
| WoS ResearcherID を名寄せに使う | 2022年発行の ID に1970年代の論文 | 過剰併合 |
| imra.eu のスクレイピング | 一覧ページなし・SSL 証明書エラー | WoS の `OG="IMRA Europe"` 検索（25件）で代替 |

                OR OG="IMRA Europe" OR OG="Aisin Seiki"

## 8. 既知の課題と対処案

優先度順。1が現在の最大のブロッカーである。

### 8.1 所属文字列の正規化（未実装・最優先）

所属文字列は生のまま格納されており、**559通りの表記**がある。豊田中央研究所だけで **129通り**に分かれている。

実際の表記の一部:

```
Toyota Central R&D Labs., Inc.                                              633件
Toyota Central R&D Laboratories, Inc., Nagakute, Aichi 480-1192, Japan       30件
Toyota Central R&D Labs., Inc., 41-1 Yokomichi, Nagakute, Aichi 480-1192, Japan  12件
Toyota Central R&amp;D Labs., Inc.  Nagakute Aichi 480‐1192 Japan             8件
Toyota Central R&amp;D Labs., Inc.  Nagakute Aichi 480‐1118 Japan             7件
TOYOTA CENTRAL R&D LABS., INC.  41-1, Yokomichi, Nagakute Aichi 480-11992 Japan
Environment and Energy Dept. II Toyota Central Research and Development Laboratories, Inc., ...
```

正規化を難しくしている要因を列挙する。

1. **HTMLエンティティが未デコード**（`R&amp;D`）。上流のパース段階の取りこぼし
2. **Unicode ハイフンの混在**（`-` U+002D と `‐` U+2010）。`480-1192` と `480‐1192` が別文字列になる
3. **正式名称の揺れ**（`Labs.` / `Labs` / `Laboratories` / `Laboratories.` / `Research and Development Laboratories`）
4. **住所の有無と粒度**（番地あり／市区まで／なし）
5. **郵便番号の誤記**（`480-1192` が正、`480-1118` `480-11992` が混入）
6. **部署名の前置**（`Environment and Energy Dept. II ...`）
7. **大文字小文字の揺れ**（`TOYOTA` / `Toyota`）

対処の方針案:

- HTMLエンティティのデコードと Unicode 正規化（NFKC＋ハイフン統一）を先に通す。これだけで表記数はかなり減る
- 組織名の**正規形辞書**を手で作り、正規表現で対応づける。559通りすべてを扱う必要はなく、上位の表記が件数の大半を占める
- 郵便番号や番地は**判定に使わない**（誤記があるため）。組織名の識別にのみ使う
- 正規化後に「どの表記がどの正規形に落ちたか」の対応表を出力し、目視できるようにする。自動で潰すと誤統合が見えなくなる
- 同時に §6.2 の豊田工業大学問題を解消する。`Toyota Technological Institute` を明示的に別組織として扱う

### 8.2 DOI 完全一致の誤対応（2件残存）

対処案は §3.6 の通り。出版年の外れ値による検算。低コストで実装できる。

### 8.3 未対応づけ67件

66件は DOI を持たない。現手法（タイトル検索＋類似度）の到達点であり、2026-08-07 以降10日間変化していない。これ以上進めるには手法を変える必要がある（掲載誌名＋年＋著者名の組み合わせ検索など）。優先度は低い。

### 8.4 低確信度154名の目視確認

イニシャル表記しかなく ORCID もない層。§5.3 のバイアスにより誤り率が4.3%より悪い可能性が高い。

### 8.5 WoS の組織別論文数がスクリプト化されていない

STATUS.md に記載した「豊田工業大学6,295件、デンソー1,457件、Toyota Research Institute 658件、JTEKT 279件、Toyota Motor Europe 278件、豊田自動織機127件」という数字が `data/derived/` に保存されていない。対象組織の範囲を決める判断に使う数字なので、再現できるようスクリプト化すべきである。

## 10. この作業から得た、繰り返し使える教訓

1. **欠損値の分布を、補完する前に必ずソース別に見る。** ランダム欠損を仮定した集計は、欠測が系統的なときに必ず誤る。§9.2 の「2018年以降」の誤認がその実例で、2週間気付かなかった。
2. **人物同定を避けられる設計を探す。** 同姓同名の曖昧さは名前を手がかりにする限り原理的に解消できない。DOI で論文を固定してから著者を引けば、この問題自体が発生しない。所属網羅率が34.5%から96.1%へ上がったのは、この一つの判断による。
3. **名寄せ規則は、誤り率を実測してから採用する。** 正解ラベルが一部にしかなくても（今回は ORCID が24%）、その部分集合で測れば規則の性質は分かる。ただし**部分集合のバイアスを明示すること**（ORCID 層はフルネーム記録層に偏る）。
4. **異常値は「捨てる」前に「なぜ異常か」を確かめる。** 研究歴74年の著者はデータの誤りではなく、ありふれた名前による識別子の併合だった。捨てていれば実在の研究者を失っていた。**除外ではなく分割が正しい対処である。**
5. **自動処理と人の判断は別ファイルに分ける。** 自動処理が毎日出力を作り直す設計では、人の判断を出力に直接書くと消える。判断表を別に持ち、毎回上から適用する。判断の履歴が残るという副次的な利点も大きい。
6. **キャッシュは成果物である。** クォータ制限のある API では、キャッシュを失うことは数日分の作業を失うことと同じ。Drive 巻き戻り事故で被害が限定的だったのはキャッシュが Drive 外にあったためである。
7. **試して外した手法を記録する。** §7 の表がそれにあたる。記録がないと同じ経路を再度試す。

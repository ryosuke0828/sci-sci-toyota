# STATUS.md の更新

`STATUS.md` は**今井泰介先生にそのまま送れる状態を常に保つ**ための文書である。

## 手順

1. `STATUS.md` を読む。
2. 前回更新以降の差分を `log.md` の最新エントリ、および `data/derived/` の出力から確認する。
3. 下記のルールに従って `STATUS.md` を書き換える。
4. 冒頭の日付を今日にする。
5. 変更点を1〜3行でユーザーに報告する。

## 文体（最重要）

**手紙として書く。** 箇条書きのメモではなく、宛名から始まり「よろしくお願いいたします」で終わる、地の文の文章にする。です・ます調。

**読み手は我々が何をやっているか知らない前提で書く。** 今井先生は課題を出した側であって、こちらの作業の中身・進め方・用語は知らない。次を必ず守る。

- **こちらが内部で使っている用語をそのまま出さない。** 「フェーズ3」「トラックA」「名寄せ」「ブロッカー」「パイロット」といった言い方は、こちらの都合の呼び名であって先生には通じない。何をする作業なのかを言葉で説明する。
- **固有名詞は初出時に一言添える。** 「OpenAlex（論文と著者の情報を無料で公開している学術データベース）」「ORCID（研究者が自分で登録する国際的な識別子）」のように。
- **数字は文章の中に置く。** 「919件を集めております」と書く。数字だけを並べた表にしない。
- **なぜそうしたのかを書く。** 手法を変えた場合は、元の案がなぜ駄目だったかを具体例とともに書く（「Suzuki で検索すると45,844件が該当してしまう」など）。結論だけ書かない。

**表を使わない。** メモ書きに見えるうえ、前提を共有していない読み手には情報が伝わらない。列挙が必要なときは文章の中で「内訳は豊田中央研究所が355件、……」と書く。どうしても表でなければ伝わらない場合に限り、1つまで。

**見出しは内容を表す日本語にする。** 「フェーズ2」ではなく「論文の情報を補う」。

## 何を書くか

- 何を目指している課題なのか（毎回冒頭に置く。先生の指示を受けた側としての理解を示す）
- これまでにできたこと。作業の流れが分かる順序で、散文で書く
- 分かったこと。特に、当初の想定と違っていた点
- いま止まっているもの。技術的に解決の見通しが立っているかどうかを明記する
- **ご判断をお願いしたいこと。** 判断に必要な背景・選択肢・こちらの推奨と、その理由をセットで書く。先生が読んだだけで判断できる状態にする
- 今後の予定

## 何を書かないか

- 作業の経緯、試行錯誤、失敗と修正の過程（`log.md` に書く）
- 実装の詳細（APIのクエリ構文、スクリプトの内部設計、ファイル名）。詳細レポートへのパス参照だけにする
- 事故やトラブルの報告。成果物の状態に影響しないものは書かない
- 「〜と思われる」「〜の可能性がある」で濁す書き方。確認できた事実か、未確認かを明示する

## 分量

A4で3〜4ページ程度。丁寧に書くと長くなるが、前提の説明を削って短くするより、読んで分かる方を優先する。検証や分析の詳細は `docs/reports/` にレポートを作り、本文からはパスで参照する。

## 更新後にやること

`git add -A && git commit && git push`（リモート: `git@github.com:ryosuke0828/sci-sci-toyota.git`）と `scripts/backup_repo.sh snapshot` を実行する。
